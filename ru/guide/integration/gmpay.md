# Интеграция с GMPay (рекомендуется) {#gmpay-integration-recommended}

Для всех новых интеграций используйте GMPay.

## Маршрут {#route}

```text
POST /payments/gmpay/v1/order/create-transaction
```

## Требование о наличии торгового удостоверения {#merchant-credential-requirement}

Перед обращением к API, создайте или проверьте строку с ключом API в панели администратора.

Что потребуется

- `pid`
- `secret_key`

`pid` необходимо передавать в запросе, а `secret_key` – это ключ для подписи.

## Минимальное тело запроса {#minimal-request-body}

```json
{
  "pid": "1000",
  "order_id": "ORD20260424001",
  "currency": "cny",
  "token": "usdt",
  "network": "tron",
  "amount": 100,
  "notify_url": "https://merchant.example.com/notify",
  "signature": "hmac-sha256-hex(...)"
}
```

## Правила подписи {#signature-rule}

> С версии `v2.0.0` GMPay использует HMAC-SHA256 вместо MD5. Обновите клиенты до развёртывания v2, иначе запросы будут получать `401 Unauthorized`. Изменение не затрагивает запросы EPay.

1. Включите все непустые поля, кроме `signature`.
2. Отсортируйте ключи в порядке ASCII.
3. Присоединяйтесь через `key=value&...`
4. Вычислите HMAC-SHA256, используя `secret_key` продавца в качестве ключа HMAC.
5. Отправьте 64-символьный шестнадцатеричный хэш в нижнем регистре в качестве `signature`.

## Связанные маршруты {#useful-companion-routes}

- `GET /payments/gmpay/v1/config`
- `POST /pay/switch-network`

Если клиенту требуются динамические сетевые/токенные опции, необходимо прочитать их из `data.supported_assets` в ответе `/payments/gmpay/v1/config`.

Прочитайте `data.site` для брендинга и `data.epay`, `data.okpay` и `data.xlayer` для настроек оформления заказа.

## Проверка уведомлений {#callback-verification}

Вызовы GMPay отправляются в формате JSON методом `POST` на URL `notify_url`.

Проверьте подпись HMAC-SHA256 и оплаченный заказ. Обрабатывайте повторные уведомления идемпотентно. Верните HTTP 200 с текстом `ok` или `success` без учёта регистра.

## Примечание об успешном ответе {#success-response-note}

Текущий источник включает `payment_url` в ответах успешного создания заказа, поэтому вызывающий получает прямой целевой URL для перенаправления на платежную систему, вместо того, чтобы самостоятельно восстанавливать этот URL.
