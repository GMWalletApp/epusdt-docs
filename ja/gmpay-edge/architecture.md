# アーキテクチャ {#architecture}

GMPay Edgeは、1つのWorkerまたは1つのBun/Nitroコンテナとして動作します。両方の実行環境は、同じ製品表面と共有の注文/決済コアを所有していますが、インフラストラクチャの適応部分は異なります。

## 製品の表面 {#product-surfaces}

- 取引先企業は、GMPayまたはEPayに対応した境界線を呼びます。
- 支払う側は、ホストされたチェックアウト機能を使用します。
- オペレーターは `/admin` を使用します。
- Telegram のユーザーは、設定されたボットを通じて相互にコミュニケーションを取ります。

## ランタイムサービス {#runtime-services}

| 能力 | Cloudflare Workers | Bun/Nitro Docker |
| --- | --- | --- |
| データベース | D1 | SQLiteを `GMPAY_DATA_DIR` に |
| キャッシュ | KV | ローカル実行時キャッシュ |
| 個人的なもの | R2 | 持続するローカルオブジェクトストレージ |
| バックグラウンドワーク | Cloudflare Queues | 堅牢なローカルキュー |
| スケジュール | Cron Triggers | バッチスケジューラ |

Bun データディレクトリには、アップロードされたファイルと、安定したキューの状態も含まれています。このディレクトリは、永続的なボリュームにマウントし、バックアップに含める必要があります。

## Cloudflare のバインディング {#cloudflare-bindings}

| バインディング | Cloudflare 製品 | 用途 |
| --- | --- | --- |
| `DB` | D1 | 信頼できるアプリケーション、支払い、認証、および配送データ |
| `CACHE` | KV | 短時間の有効期限を持つキャッシュと、関連するテレメトリ |
| `FILES` | R2 | プライベートな支払いレビューの証拠と、生成されたエクスポート |
| `PAYMENT_QUEUE` | キュー | 非同期決済スキャン |
| `WEBHOOK_QUEUE` | キュー | 非同期の商取引 Webhook の配信 |

## バックグラウンドワーク {#background-work}

特定の実行環境向けの堅牢なキューとスケジューラは、決済スキャンやWebフックの再試行を、同期リクエストの外で行います。また、決済の有効期限管理、クリーンアップ、接続の健全性チェック、およびレート同期も処理します。

Webhook の配信は、堅牢なアウトボックスを使用し、再試行履歴、手動での再試行、および両方の実行環境における監査記録を利用します。

## データとセキュリティモデル {#data-and-security-model}

- 選択された実行環境において、D1 または SQLite が基準となります。
- キャッシュとプライベートオブジェクトストレージは、選択されたランタイムの適応を使用します。
- 支払いアダプターは読み取り専用です。
- 管理部門は、Better Auth、TOTP、および動的マルチロールRBACを使用しています。

## プロトコルの境界 {#protocol-boundaries}

GMPayは**HMAC-SHA256**の署名を使用します。EPayとの互換性は、古い**MD5**の形式に依存しています。送信側のリターンの場合、元のプロトコルの署名形式を維持します。
